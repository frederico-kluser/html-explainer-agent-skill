O construtor de prompt: o que esta rodada mudou na skill

A skill ganhou uma aba opcional que remonta um prompt XML a cada clique. Este documento foi gerado por ela, e a última aba é a própria feature funcionando.

html-explainer 1.1.0 13 commits 333 testes · 0 falhas ago/2026

O que mudou

A skill passou a saber gerar um construtor de prompt, e só quando pedem. É uma aba a mais no documento: perguntas de radio, checkbox, text e textarea à esquerda; à direita, o prompt XML remontado a cada clique, com botão de copiar. Um documento normal do html-explainer continua saindo exatamente como saía — zero caractere a mais.

O pedido original era literal: "o prompt é definido em XML, o usuário responde perguntas com checkbox ou radio, e de acordo com o que ele escolher muda o HTML final gerando um construtor de prompt, com um botão de copiar, e o construtor tem sua própria aba." É isso que a aba Construtor deste arquivo faz.

A linha que liga a feature

Uma flag no gerador que já existia. Sem --builder nada disto é carregado:

node html-explainer/scripts/new-doc.mjs "Plano da migração" ./plano.html --builder

O documento sai com a aba pronta e funcionando — não com um esqueleto para preencher. O fluxo mais comum é o outro, com as perguntas do seu caso:

node html-explainer/scripts/new-builder.mjs --example > spec.xml   # edite as perguntas
node html-explainer/scripts/new-builder.mjs spec.xml --into ./plano.html
node html-explainer/scripts/check-doc.mjs ./plano.html

Foi assim que este arquivo nasceu — com a spec da aba Construtor, que monta o prompt para pedir a próxima rodada de trabalho neste mesmo repositório.

O que NÃO mudou — e é o ponto

Zero dependência

Nenhum node_modules, nenhum lockfile, nenhum npm install. A suíte inteira é node:test. O documento continua puxando tudo de CDN.

Um arquivo

O construtor viaja dentro do .html: spec, casca e runtime. Salvar, mandar por anexo, abrir por duplo clique — continua valendo com construtor.

Desligado por padrão

Sem --builder o new-doc.mjs escreve o mesmo arquivo de sempre. O passo 5 do SKILL.md é condicional, não um sexto passo.

A demonstração mais honesta: este arquivo passa no próprio linter com 0 erros e 0 avisos, e o prompt escrito no HTML da aba Construtor é byte a byte (2497 bytes, 53 linhas) o que o runtime monta com os padrões. A aba De-para mostra como isso é provado.

Como funciona

Ninguém escreve o HTML do formulário — o runtime o gera a partir de uma spec XML. Essa é a decisão de onde tudo o mais decorre, e ela existe por um motivo específico: numa skill cuja obsessão declarada é markup ARIA correto, deixar um humano escrever id, for e aria-* à mão para vinte controles é convidar exatamente o erro que a skill inteira existe para evitar.

Os três blocos, e o que cada um faz

BlocoÉQuem o lê
pb:spec Um <script type="application/xml"> com as perguntas, os fragmentos e o esqueleto do prompt. O runtime, com DOMParser. E o linter, no HTML cru.
pb:shell A casca: um [data-pb-form] vazio, os botões, e o <code data-pb-output> já preenchido. O runtime preenche o formulário; o navegador exibe o resto.
pb:runtime 392 linhas de JS próprio, o último <script> do arquivo. O navegador — e o Node, quando o gerador precisa recalcular a saída.

Por que a spec é XML inerte dentro do arquivo

type="application/xml" é o ponto inteiro: o navegador não executa o bloco e não parseia o conteúdo como HTML — ele fica texto cru até o fechamento. É o que permite declarar markup dentro de markup sem build e sem escapar nada:

<question id="frente" type="radio" label="Qual frente atacar">
  <option value="dividas" label="Fechar as dívidas" default="true"><![CDATA[<front id="dividas">
  Feche as dívidas que a rodada anterior registrou de propósito, e só elas.
</front>]]></option>
</question>

O corpo do <option> — o fragmento que entra no prompt quando ela está marcada — vive em CDATA, porque é XML e não pode ser reinterpretado. Com o bloco inerte, o custo disso é zero: nem o navegador nem o parser de HTML olham para dentro.

O linter valida a spec, não o DOM

O DOM do formulário não existe em disco — ele nasce no navegador. Um linter de arquivo nunca o veria. A escolha foi validar a fonte, e ela acabou sendo uma checagem mais forte do que olhar o resultado: erros que só apareceriam como comportamento errado viram erro de arquivo.

Só olhando o DOM gerado

Um radio sem default gera markup impecável — e abre na primeira opção do XML. O documento fica correto e errado: o padrão passa a ser a ordem em que alguém digitou.

Olhando a spec

radio sem exatamente um default é erro. Junto com {{marcador}} órfão, id de pergunta duplicado e join fora dos quatro valores.

As duas linhas do <script> "congelado"

A skill manda copiar o runtime do template inteiro e não editar. Esta rodada mudou duas linhas dele — as únicas que ele já sofreu — e as duas estão lá mesmo em documento sem construtor, para que o gancho nunca falte quando alguém acrescentar a aba depois.

A primeira faz o cache de fonte crua pular blocos vivos:

document.querySelectorAll('pre > code').forEach(function (code) {
  if (code.closest('[data-live]')) return;   // texto muda em runtime: leia na hora do clique
  sources.set(code, code.textContent.replace(/\n$/, ''));
});

Sem ela o documento mente de um jeito difícil de perceber: o cache é tirado uma vez só, no load, então o botãozinho de hover entregaria para sempre o prompt do momento em que a página abriu, por mais que o formulário mudasse. O bug só aparece se você copiar depois de clicar em alguma coisa.

A segunda expõe o caminho de cópia — navigator.clipboard com o fallback execCommand — para o botão grande do construtor reusar:

window.__explainerCopy = copyText;

A alternativa era uma segunda implementação de cópia dentro do runtime do construtor. Duas cópias da mesma lógica divergem no primeiro caso de borda, e o caso de borda aqui é justamente o file://, que é o modo em que o documento é feito para ser aberto.

O bloco pré-preenchido é recomputado, nunca copiado

O <code data-pb-output> nasce com o prompt padrão já dentro, escapado. Ele existe para que três leitores diferentes recebam o mesmo texto: quem abre sem JavaScript, quem imprime em PDF e quem lê o view-source.

Se esse texto não bater com o que o JavaScript monta, o documento mente para metade dos leitores — e ninguém percebe, porque as duas versões nunca aparecem na mesma tela. Por isso o gerador não copia esse bloco de lugar nenhum: ele roda o runtime real do documento dentro do Node e escreve o resultado.

// o runtime foi escrito para isto: instala __promptBuilder no global e SÓ DEPOIS
// pergunta se existe `document`. Em Node não existe, e a execução para ali.
new Function(runtimeSource())();
const PB = globalThis.__promptBuilder;
const prompt = PB.build(model, PB.defaults(model));   // é este texto que vai para o HTML

É a mesma função que o navegador chamará no primeiro clique. Não há segunda implementação da montagem para divergir — e a aba De-para mostra o comando que prova a identidade byte a byte neste arquivo.

Na carga, quem destaca é o highlightAll

O construtor não chama hljs.highlightElement() na primeira montagem quando document.readyState === 'loading'. Nesse instante o hljs.highlightAll() do runtime do template já deixou um ouvinte de DOMContentLoaded agendado. A condição certa não é "este bloco já foi destacado?" — na carga o atributo ainda nem existe — é "há um highlightAll a caminho?":

var hlPendente = doc.readyState === 'loading';
refresh(false, hlPendente);                    // com deferHl: escreve o texto, não destaca
if (hlPendente) global.addEventListener('DOMContentLoaded', function () {
  // rede de segurança: registrado DEPOIS do ouvinte do highlightAll, logo roda depois dele.
  if (!out.dataset.highlighted && global.hljs) global.hljs.highlightElement(out);
});

Na remontagem — todo clique dali em diante — vale a receita normal: textContent, depois delete code.dataset.highlighted, depois highlightElement. Sem o delete, o highlight.js 11.9+ recusa re-destacar e escreve no console.

Por que o parser de atributos próprio, em vez de [^>]*? Porque XML 1.0 só proíbe < e & crus em valor de atributo — o > é legal, e o DOMParser aceita:

const ATTRS_SRC = '((?:"[^"]*"|\'[^\']*\'|[^>"\'])*)';

Com [^>]*, uma pergunta rotulada label="custo > 0" teria a tag cortada ao meio e apareceria como "pergunta sem label" — erro inventado num documento correto. As três alternativas começam em caracteres disjuntos, então não há backtracking a explorar.

O que quase passou

Onze defeitos chegaram até a revisão adversarial, e todos passavam no teste feliz. Dez estão aqui; o décimo primeiro — o aviso do hljs em toda carga — está em Como funciona, porque a correção dele virou arquitetura. Nenhum deles quebra na tela. Cada um entrega o resultado errado, ou nenhum resultado, com cara de sucesso — e é por isso que esta é a aba que vale a leitura.

O padrão que aparece em nove dos onze: a coisa funciona, só que errado, e o código de saída é 0. Teste que só verifica "passou?" não pega nenhum deles.

O linter aprovava o formulário que abria na opção errada

O runtime compara getAttribute('default') === 'true' — com a string. O linter aceitava o atributo pelado.

<option value="a" label="Primeira"/>
<option value="b" label="Segunda" default/>   <!-- passava limpo... -->

A spec passava, o documento abria — na primeira opção. O formulário parecia funcionar; o padrão do documento é que era outro. Correção: default com qualquer valor que não seja "true" ou "false" é erro.

E o teste que a correção pediu revelou um segundo defeito na mesma família: a busca pela palavra default varria a tag inteira, então um label como "Padrão do projeto" — ou qualquer rótulo com a palavra "default" — contava como default. Falso positivo e falso negativo na mesma linha: uma opção ganhava default que não tinha, e o radio que realmente estava sem default passava por ter dois.

O attrsOf() lê as duas aspas e também o valor sem aspas, como o parser do navegador.

Vizinho do mesmo bug, e mais sutil: a peneira de classe casava por substring. const cls = a.get('class');
if (!cls || !cls.split(/\s+/).includes('prompt-builder')) continue;

Comentar a spec reprovava a spec

Comentar uma spec XML é justamente escrever "escolha a <question> e a <option> certas". Sem apagar o comentário antes de contar as tags, essa frase virava uma pergunta fantasma — sem id e sem type — e reprovava um documento perfeito.

A correção recusou a solução óbvia. Dois replace em sequência têm caso-veneno nas duas ordens:

EntradaO que é, de verdadeQuem erra
<!-- ]]> --> Um comentário inteiro; o ]]> de dentro é texto. Quem apaga CDATA primeiro.
<![CDATA[ <!-- ]]> Um CDATA inteiro; o <!-- de dentro é texto. Quem apaga comentário primeiro.

O que foi feito no lugar é uma varredura linear que imita a regra do próprio XML — comentário e CDATA não se aninham, e quem abre primeiro manda:

for (;;) {
  const c = body.indexOf('<!--', i);
  const d = body.indexOf('<![CDATA[', i);
  if (c === -1 && d === -1) break;
  if (d === -1 || (c !== -1 && c < d)) { /* comentário */ }
  else { /* CDATA */ }
}

Ela também distingue os dois usos que o linter faz do texto: as tags são contadas com comentário e CDATA em branco; os {{marcadores}} são procurados com o CDATA intacto, porque é lá que eles moram. Assim um marcador comentado não vira marcador fantasma e nenhum marcador de verdade some. De brinde, a varredura é O(n) — a lentidão era o defeito.

O gerador não rodava pelo modo de instalação oficial

O install.sh instala a skill como symlink do diretório inteiro. O new-builder.mjs tinha a guarda "fui executado ou fui importado?" escrita assim:

if (process.argv[1] && resolve(process.argv[1]) === fileURLToPath(import.meta.url)) {

O loader ESM do Node resolve symlink antes de formar import.meta.url. O resolve() só normaliza . e .. — não resolve symlink. Pelo caminho do link os dois lados nunca batiam:

0 linhas de saída, código de saída 0, nenhuma mensagem. --example > spec.xml criava um arquivo vazio, e nada no terminal dizia por quê.

A correção passa realpathSync nos dois lados, com o resolve() antigo como rede de segurança para quando o realpath falhar (arquivo apagado sob os pés, permissão negada num diretório do caminho):

function executadoDiretamente() {
  const argv1 = process.argv[1];
  if (!argv1) return false;
  const aqui = fileURLToPath(import.meta.url);
  const real = (p) => { try { return realpathSync(p); } catch { return resolve(p); } };
  return real(argv1) === real(aqui) || resolve(argv1) === aqui;
}

process.exit() descartava a saída no cano

Quando o stdout é um cano — | pbcopy, | less, CI, outro agente com spawn — a escrita do Node é assíncrona. O que não coube no buffer fica numa fila interna, e process.exit() derruba o processo jogando essa fila fora. Para arquivo a escrita é síncrona, e é por isso que o > saida.html do README nunca truncou — o que fazia o bug parecer inofensivo.

ScriptEntregue no canoCódigo de saída
escape-code.mjs --raw8192 de 837 780 bytes (1%)0
new-builder.mjs (blocos)8021 de 27 502 bytes0

A correção é a mesma nos quatro scripts: o corpo vive numa função, cada saída antecipada é um return com o código, e o topo do arquivo faz process.exitCode = main(). O Node termina sozinho, depois de drenar tudo, com o mesmo código. Um único critério nos quatro é o que impede que a próxima linha nova erre de novo.

Efeito colateral útil: o escape-code.mjs passou a poder ser usado com | sem perder conteúdo, que é como um agente costuma chamá-lo.

Dívida

Três defeitos ficaram no repositório de propósito, com teste que os denuncia. Todos são anteriores ao construtor e nenhum tem relação com ele. Consertar defeito pré-existente no meio de uma feature é como se entrelaçam dois diffs que ninguém mais consegue revisar.

Eles não estão num arquivo de anotações: estão na suíte, marcados como todo. Um todo não derruba node --test e não some da vista — no dia em que a correção chegar, o teste vira verde sozinho e o marcador sai.

1 e 2. Aspas simples são invisíveis para o linter antigo

Os regexes de structure, externals e codeBlocks só leem valor entre aspas duplas. O attrsOf() que a Onda 1 escreveu para o construtor já lê as duas — a dívida é o código velho não usá-lo:

// check-doc.mjs:191 — ids duplicados
for (const m of masked.matchAll(/\bid\s*=\s*"([^"]+)"/g)) {

Três sintomas, um por teste todo:

EntradaDevia serÉ
<div id='x'></div><div id='x'></div> erro: id duplicado passa limpo
<img src='grafico.png'> erro: aponta para arquivo ao lado passa limpo — e a regra "um arquivo, sempre" é a primeira da skill
<pre title="a > b"> erro: bloco sem class="language-XXX" o bloco inteiro some da análise

O terceiro é o mesmo [^>]* que o parser novo já resolveu do lado do construtor: um > dentro do valor de um atributo corta a tag ao meio.

3. mask() e maskCode() são quadráticos

Os dois usam replace com corpo preguiçoso. Cada abertura de <pre relança a varredura, então um documento com muitas aberturas custa O(n²):

.replace(/(<pre\b[^>]*>)([\s\S]*?)(<\/pre>)/gi, blank)
.replace(/(<code\b[^>]*>)([\s\S]*?)(<\/code>)/gi, blank)

A correção já existe no mesmo arquivo, escrita para outra função: o preRanges() varre à mão, e o comentário dele diz por quê. É a receita para quando o conserto chegar:

/**
 * Faixas [index, end) de cada <pre>…</pre>, com a marca de `data-live`. Varrido à mão:
 * o regex equivalente (`<pre…>[\s\S]*?</pre>`) tenta o corpo a partir de CADA `<pre`
 * e fica quadrático num documento com muitos `<pre` sem fechar.
 */

Na prática ninguém vai notar: o maior documento da skill tem 60 954 bytes e o linter termina em fração de segundo. A dívida importa porque a classe do problema é conhecida e a correção já está escrita ao lado.
